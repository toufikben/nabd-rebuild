# خطة Hotfix عاجلة: التشفير والاشتراكات

**المستودع:** `toufikben/nabd-rebuild`
**نطاق الخطة:** `R-Data & Security` و`R-Monetization` فقط
**تاريخ الإعداد:** 2026-09-22
**المرجع:** تقرير الفحص الشامل للمستودع على commit `7493fd8`

## 1. قرار الإطلاق

يجب تجميد أي إصدار إنتاجي جديد إلى أن تُغلق البنود الحرجة التالية:

1. إيقاف `rotateKey()` الهدّام أو استبداله بتدوير ذري يحافظ على البيانات.
2. منع مشاركة بيانات المذكرات كنص JSON غير مشفر من شاشة Settings.
3. منع إدراج مفاتيح entitlement في النسخ الاحتياطية عند الإنشاء.
4. منع منح Pro للاشتراكات الشهرية والسنوية قبل وصول تحقق موثوق من المتجر عبر خادم أو خدمة entitlement موثوقة.

إصلاح `Info.plist` وApp Links وAdMob مهم للإصدار، لكنه يدخل في مسار Release Gate المرافق وليس في أول commit أمني إذا كان فصل التغييرات ضروريًا.

## 2. استراتيجية التنفيذ

يُنفذ العمل في فرعين منفصلين لتقليل مساحة الخطر:

| الفرع | الهدف | سياسة الدمج |
|---|---|---|
| `hotfix/data-protection` | إصلاح key rotation، التصدير، وفلترة النسخ | لا يدمج قبل نجاح اختبارات البيانات والاستعادة |
| `hotfix/entitlement` | ربط الاشتراكات بتحقق موثوق وتخزين entitlement | لا يدمج قبل اختبارات الحالات المنتهية والمُلغاة والمُستردة |

كل commit يجب أن يكون صغيرًا وقابلًا للتراجع. لا تُخلط إعادة تصميم الواجهة أو i18n أو تحسينات غير مرتبطة داخل هذه الفروع.

## 3. المسار الأول: حماية التشفير والبيانات

### 3.1 إيقاف الخطر فورًا

**الإجراء الأول:** تحويل `EncryptionService.rotateKey()` إلى فشل صريح غير هدّام، أو جعله خاصًا داخليًا مؤقتًا، إلى أن يُنفذ التدوير الآمن.

السلوك المطلوب مؤقتًا:

- لا يُكتب مفتاح جديد فوق المفتاح الحالي.
- لا تُحذف صناديق Hive بسبب استدعاء غير مدعوم.
- يُرمى استثناء واضح مثل `UnsupportedError` أو استثناء نطاقي مخصص.
- يُضاف اختبار يثبت أن استدعاء API لا يغير المفتاح ولا يفسد البيانات.
- يبقى `PrivacyService.deleteEverything()` مسارًا مستقلًا ومحدد السياسة، ولا يعتمد على API غير آمن.

هذا الإجراء يمنع فقد البيانات فورًا، حتى قبل اكتمال التدوير الحقيقي.

### 3.2 تنفيذ تدوير مفتاح آمن

بعد تعطيل API الهدّام، يُنفذ التدوير الحقيقي كعملية قابلة للاستئناف:

1. قراءة المفتاح القديم وفتح كل الصناديق الحالية بالمفتاح القديم.
2. إنشاء مفتاح جديد في الذاكرة فقط.
3. نسخ محتوى كل صندوق إلى صناديق staging مشفرة بالمفتاح الجديد.
4. تنفيذ `flush` والتحقق من عدد المفاتيح والقيم وإمكانية إعادة القراءة بالمفتاح الجديد.
5. كتابة marker يوضح المرحلة الحالية، مثل `started` أو `staged` أو `verified`.
6. إغلاق الصناديق القديمة والجديدة بأمان.
7. تبديل المفتاح في Secure Storage فقط بعد اكتمال التحقق.
8. إعادة فتح الصناديق بالمفتاح الجديد والتحقق مرة أخرى.
9. حذف staging والبيانات القديمة فقط بعد نجاح الفتح النهائي.
10. عند الفشل، استخدام marker لاستئناف العملية أو rollback إلى المفتاح القديم دون حذف المصدر.

لا يُسمح بحذف المصدر قبل وجود نسخة staging قابلة للقراءة والتحقق.

### 3.3 حماية التصدير

يجب توحيد زر `Export Data` مع `BackupService` بدل `Share.share` للنص الخام.

السلوك المقترح للـ Hotfix:

- زر التصدير ينشئ ملف backup مشفرًا بكلمة مرور يحددها المستخدم.
- لا يُرسل محتوى المذكرات مباشرة إلى `Share.share`.
- إذا تعذر فرض كلمة مرور في UX الحالي، يجب إيقاف التصدير مؤقتًا برسالة صريحة بدل تسريب JSON بلا تحذير.
- اسم الملف وامتداده يجب أن يميزا النسخة المشفرة عن ملف نصي عادي.
- أخطاء كلمة المرور أو MAC أو الملف التالف تظهر كفشل استعادة واضح، ولا تُطبق أي بيانات جزئيًا.

### 3.4 فلترة entitlement عند إنشاء النسخة

تُطبق قائمة حظر واحدة قبل بناء archive payload، وليس عند الاستعادة فقط:

```text
is_pro
is_lifetime
pro_expiry
```

يجب تطبيقها على `settings.json` وعلى أي payload آخر قد يحمل حالة Pro، بما في ذلك `achievements.json` إذا كان يُستخدم لحفظ الحالة نفسها.

الاختبار المطلوب لا يكتفي باستدعاء دالة filter؛ بل ينشئ backup فعليًا ويفك ضغط الجزء الداخلي قبل التشفير ويتأكد من عدم وجود المفاتيح المحظورة.

### 3.5 سياسة Delete All Data

قبل الدمج، يجب اتخاذ قرار منتجي مكتوب:

- إذا كان المقصود حذف البيانات فقط مع إبقاء التطبيق قابلًا للاستخدام، يُنشأ مفتاح جديد بعد حذف الصناديق، لكن يجب اختبار عدم إمكانية فتح البيانات القديمة.
- إذا كان المقصود محوًا غير قابل للاسترجاع، يُحذف مفتاح Secure Storage بعد نجاح حذف الصناديق والوسائط، ثم يُنشأ مفتاح جديد عند بدء جلسة بيانات جديدة.

لا يُستخدم `rotateKey()` الحالي لتحقيق أي من القرارين.

## 4. المسار الثاني: entitlement للاشتراكات

### 4.1 قاعدة الأمان

حتى يتم التحقق من الشراء عبر جهة موثوقة، تكون النتيجة الافتراضية للاشتراك الشهري والسنوي هي **غير مشترك**. لا يجوز أن تمنح callback من متجر الجهاز وحده حالة Pro دائمة أو قابلة للتزوير.

الشراء المحلي يثبت أن المتجر أرسل حدثًا، لكنه لا يكفي وحده لإثبات الصلاحية النهائية أو التجديد أو الإلغاء أو الاسترداد.

### 4.2 قرار البنية قبل البرمجة

يجب اختيار مسار واحد خلال بداية التنفيذ:

| الخيار | متى يستخدم | المطلوب |
|---|---|---|
| خدمة entitlement موثوقة مثل RevenueCat | أسرع Hotfix وأقل كود خادمي مخصص | إنشاء مشروع، ربط المنتجات، إضافة مفاتيح عامة للتطبيق فقط، واستخدام SDK للتحقق من الحالة |
| Backend مخصص للتحقق | إذا كانت هناك متطلبات ملكية بيانات أو منطق تجاري خاص | endpoint آمن يستقبل purchase token/receipt، يتحقق عبر Google/Apple، ويعيد entitlement موقعًا أو موثقًا |

القاعدة: **لا توضع مفاتيح Google Play service account أو App Store private key داخل التطبيق أو المستودع.**

إذا لم يُتخذ القرار أو لم تتوفر الخدمة، يبقى الاشتراك الشهري والسنوي غير مفعّل في Release، ويستمر Lifetime فقط وفق سياسة تحقق مستقلة ومختبرة.

### 4.3 نموذج entitlement موحد

ينبغي أن يعيد verifier نموذجًا واحدًا بدل اعتماد الواجهة على callback خام:

| الحقل | الغرض |
|---|---|
| `productId` | المنتج الموثق |
| `status` | `active`, `grace`, `expired`, `revoked`, `unverified` |
| `expiresAt` | نهاية الصلاحية التي أكدها المتجر |
| `isLifetime` | تمييز الشراء الدائم |
| `source` | Google Play أو App Store |
| `verifiedAt` | وقت آخر تحقق |
| `entitlementId` | معرف العملية أو الاشتراك دون تخزين أسرار غير لازمة |

لا يُستنتج `active` من الساعة المحلية وحدها. عند انقطاع الشبكة، تُستخدم آخر حالة موثقة ضمن سياسة offline قصيرة ومحددة، ثم يعود التطبيق إلى `unverified` بعد انتهائها.

### 4.4 دورة الشراء والاستعادة

التدفق المطلوب:

1. يستلم التطبيق purchase update.
2. يتحقق من اكتمال الشراء ووجود product ID متوقع.
3. يرسل token/receipt إلى verifier عبر قناة HTTPS.
4. يتحقق verifier من package/bundle ID، المنتج، حالة الشراء، expiry، acknowledgement، وtrial/intro offer عند وجودها.
5. يعيد verifier entitlement موثقًا.
6. يحفظ التطبيق أقل قدر لازم من الحالة، ويفضل entitlement موقّعًا أو معرفًا يمكن إعادة التحقق منه.
7. يمنح Pro فقط عند `active` أو `grace` وفق سياسة المنتج.
8. يعالج الاسترداد والإلغاء والانتهاء بإزالة Pro بعد تأكيد verifier.
9. يستدعي `completePurchase` في الموضع الصحيح بعد معالجة الحدث، وفق عقد مكتبة الشراء الحالية.

### 4.5 حالات يجب إغلاقها قبل الدمج

| الحالة | النتيجة المقبولة |
|---|---|
| مستخدم بلا شراء | Free limits، ولا Pro |
| شراء شهري جديد | Pro فقط بعد verifier |
| شراء سنوي جديد | Pro فقط بعد verifier |
| تجربة مجانية من المتجر | Pro حتى expiry الموثق |
| إلغاء أثناء الفترة | Pro حتى expiry، ثم ينتهي |
| تجديد ناجح | تمديد `expiresAt` الموثق |
| استرداد أو revocation | إزالة Pro بعد تحديث verifier |
| انتهاء الاشتراك | إزالة Pro وعدم الاعتماد على cache قديم |
| Restore Purchases | إعادة entitlement بعد تحقق جديد |
| token تالف أو منتج غير متوقع | رفض، تسجيل آمن، وعدم منح Pro |
| الشبكة غير متاحة | آخر entitlement صالح ضمن TTL، ثم `unverified` |
| تلاعب بالساعة المحلية | لا يمدد Pro |

## 5. ترتيب التنفيذ الزمني

### المرحلة H0 — احتواء الخطر

**النتيجة المطلوبة:** لا يوجد مسار معروف يبدل المفتاح ويكسر البيانات أو يشارك JSON الخام.

- تعطيل `rotateKey()` الهدّام.
- تعطيل التصدير الخام أو ربطه بالنسخة المشفرة.
- إضافة اختبارات منع regression.
- إضافة feature flag أو kill switch لتعطيل الاشتراكات الشهرية والسنوية في Release إذا لم يكتمل verifier.

### المرحلة H1 — إصلاح النسخ الاحتياطي

**النتيجة المطلوبة:** backup مشفر ولا يحمل entitlement.

- فلترة payload عند الإنشاء.
- اختبار فك ضغط payload الداخلي.
- اختبار كلمة مرور خاطئة وMAC تالف وملف ناقص.
- اختبار restore ذري مع rollback وعدم الكتابة الجزئية.

### المرحلة H2 — تدوير المفتاح

**النتيجة المطلوبة:** تدوير اختياري آمن، أو إزالة API نهائيًا إذا لم تكن هناك حاجة منتجية له.

- staging وmarkers وverification.
- اختبار بيانات متعددة الصناديق ووسائط.
- اختبار فشل في كل مرحلة واستئناف أو rollback.
- اختبار إعادة تشغيل التطبيق بعد التدوير.

### المرحلة H3 — entitlement

**النتيجة المطلوبة:** لا Pro للاشتراكات إلا بعد تحقق موثوق.

- اختيار RevenueCat أو backend مخصص.
- تنفيذ verifier adapter خلف واجهة مستقلة عن SDK.
- تخزين حالة موثقة مع TTL.
- إضافة اختبارات unit وintegration للحالات المذكورة.
- إبقاء subscription UI صريحًا بأن الحالة قيد التحقق عند الحاجة.

### المرحلة H4 — Release Gate

**النتيجة المطلوبة:** إصدار قابل للنشر دون عودة الخطر.

- `flutter analyze` بلا أخطاء.
- كل الاختبارات ناجحة.
- Debug وRelease APK/AAB ناجحة.
- اختبار جهاز أو emulator للنسخ والاستعادة والقفل والشراء والاسترداد.
- مراجعة عدم وجود أسرار backend في Git أو binary configuration.
- تحديث `ROADMAP.md` و`MONETIZATION_GUIDE.md` بنتيجة فعلية وcommit الجديد.

## 7. خطة التراجع والاستجابة

إذا فشل Hotfix بعد النشر:

1. تعطيل الاشتراكات الشهرية والسنوية عبر feature flag أو إعداد release آمن.
2. عدم تشغيل أي key rotation تلقائي عند startup أو migration.
3. إبقاء backup restore القديم للقراءة فقط إذا ثبتت سلامته، وعدم حذف ملفات المستخدم.
4. إصدار patch يعيد التصدير إلى وضع disabled بدل العودة إلى JSON الخام.
5. الحفاظ على المفتاح القديم وعدم حذفه أثناء التحقيق.
6. جمع logs تقنية غير حساسة: نوع الفشل، الإصدار، مرحلة العملية، دون محتوى المذكرات أو tokens.
7. نشر رسالة للمستخدم عند الحاجة تطلب عدم حذف التطبيق قبل توفير مسار استعادة.

## 8. تعريف الإنجاز النهائي

لا تُغلق خطة Hotfix إلا إذا تحققت الشروط التالية مجتمعة:

- لا توجد دالة عامة تستبدل مفتاح Hive فوق بيانات قائمة دون إعادة تشفير متحقق.
- لا يشارك التطبيق محتوى المذكرات كنص خام من Settings.
- لا تحتوي النسخة الاحتياطية المنشأة على `is_pro` أو `is_lifetime` أو `pro_expiry`.
- الاستعادة فشلها ذري ولا تترك بيانات جزئية.
- كل subscription entitlement يأتي من verifier موثوق أو تكون الاشتراكات معطلة.
- الإلغاء والاسترداد والانتهاء والتجديد تعكس الحالة في التطبيق.
- اختبارات CI وruntime ناجحة، مع توثيق commit ورقم الاختبارات الجديدين.
- لا توجد أسرار backend في الكود أو `--dart-define` المضمّن في المستودع.

## 9. ما لا يدخل في Hotfix

تُؤجل إلى خطة منفصلة بعد إغلاق الخطر: إعادة تصميم i18n الكامل، تحسينات الصوت والرسوم، توسيع الميزات الاجتماعية، تغيير هوية المنتج، إصلاحات UX غير المرتبطة بالحماية، وترقية GitHub Actions غير الضرورية لنجاح Hotfix.
